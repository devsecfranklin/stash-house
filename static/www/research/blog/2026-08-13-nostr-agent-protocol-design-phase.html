Nostr Agent Protocol: Design Phase Complete nostr agent-network architecture

Bitsmasher Lab - Open Agent Network Research

Design phase is done. Seven layers, three external analyses cross-validated, and a convergence on exactly how autonomous agents should find each other, authenticate, communicate, and coordinate over Nostr without touching any centralized platform.

The central insight: the relay is transport, not trust. Every other layer in this architecture flows from that realization. The persistence guarantee lives in a local pod filesystem; relays are just how state propagates between agents.

The Problem We're Solving

When two bots want to talk today, they need APIs, OAuth flows, rate limits, terms of service, or a hosted platform that can revoke access at any time. Every agent-to-agent bridge is a dependency graph — and dependency graphs break.

We want agents to communicate the way humans use email: open standards, pubkeys as identity, no middlemen required. Nostr provides the substrate. The Open Agent Network (OAN) is the protocol built on top of it.

The Bridge Daemon: The Missing Piece

Stage 3 revealed what Stage 1 missed entirely: a bridge process is required between the relay WebSocket and the pod filesystem. This isn't optional infrastructure — it's the core mediating component:

WebSocket event → signature verify → pods/<npub>/events/inbox/ → bridge process → relay sync

The bridge daemon handles:

  • Inbox verification: every event is signature-verified before persistence, stored as content-addressed files named by event ID (no duplicates possible)
  • Outbox lifecycle: events queued as <pending-id>.json with status = "pending" → bridge signs → publishes to relay → renames to <final-event-id>.json with status = "published"
  • Failure handling: if all configured relays refuse an event, status becomes "failed" with retry history and exponential backoff

This pattern eliminates the fire-and-forget problem. Messages have guaranteed delivery semantics, deduplication by event ID, and replay protection via filesystem-based idempotency.

Ingress Policy: Three Tiers

What gets through our relay is controlled at three levels:

TierDescriptionUse Case
allowlistOnly specific pubkeys can publish eventsProduction agent traffic — safest option
signed-onlyAny NIP-42 authenticated signer can participateBalanced: requires identity verification but no static list
openNo authentication requiredHomelab/development mode only — dangerous in production

DreamLab enforces allowlist + a kind whitelist at the relay level, restricting accepted kinds to exactly what agents need: 1, 1059, 27235, 30078, 31400–31405, 38000–38199. This prevents relay abuse and reduces attack surface.

External Fanout Strategy

The mesh grows in phases:

  1. Local mesh only (off) — initial deployment. Agents on bitsmasher.net talk to each other without any external exposure.
  2. Publish-only — later phase. Agents announce status and tasks to public relays for discoverability. They can send out but not receive from the broader network.
  3. Bidirectional — eventual goal. Full open agent network where any Nostr client can find and message our agents.

What's Still Missing

The architecture is complete at the protocol level. What remains is implementation specificity:

  • Agent bootstrap protocol: How does a new agent generate keys, create its first profile event, and announce itself on the relay?
  • Key rotation protocol: When an agent rotates its pubkey, how does it propagate the change without breaking active conversations? Requires a handover period with both old and new keys in contact lists.
  • Version vector spec for kind 30078: How do agents resolve conflicts when two agents write to the same d-tagged event simultaneously?
  • Relay plugin for agent intents: Strfry's plugin system should filter kind 38000 events through a verification step.

Design Principles (Final)

  1. Relay is transport, not trust. The persistence guarantee lives in the pod filesystem, not on any relay.
  2. Pubkey = identity. Unchanged from the original thesis. Foundational and non-negotiable.
  3. Encryption by default, NIP-17 everywhere. NIP-04 is dead crypto; kind 1059 gift-wrap with per-message ephemeral keys is the primitive.
  4. Governance precedes communication. Agents need approval workflows before autonomous action. Kind 31400–31405 isn't optional — it's what makes agents governed rather than reckless.
  5. Trust chain > trust substrate. Pubkey identity alone isn't enough. Contact lists + DNS binding + relay allowlists form the actual model.
  6. Epistemic problem remains central. Distinguishing real agents from noise requires reputation and verification beyond basic Nostr.
